## 1. Цель проекта

Мобильное приложение под **Android** для учителя. Оно хранит расписание уроков по конкретным датам и напоминает о них уведомлениями.

### Требования (от владельца)

1. Составлять расписание на неделю.
2. Для каждого урока указывать: **дату, время начала и конца, класс, кабинет, тему**.
3. За час до первого урока дня появляется уведомление «Следующий урок …» (см. 3.4).
4. **За 5 минут до конца урока** уведомление сменяется на «Скоро конец урока» со звуком и **вибрацией**; везде есть обратный отсчёт.
5. **После окончания урока** появляется уведомление о следующем уроке (если уроки без перемены, сразу «Идёт урок»). Состояния сменяют друг друга: в шторке одно уведомление приложения, всё срабатывает по таймеру системы без открытия приложения.
6. Тема урока меняется почти каждую неделю, её нужно легко редактировать.
7. Должна быть возможность **просматривать расписание прошлых недель**.
8. Кнопка **«Скопировать неделю»**: выбрать предыдущую неделю и скопировать её уроки на текущую.
9. Формат даты в интерфейсе: **ДД.ММ.ГГГГ** (например, 25.12.2026).

### Контекст владельца

- Опыт: React (веб). Kotlin не знает, поэтому выбран React Native.
- **Цель двойная:** сделать приложение и **научиться писать на React Native**. Поэтому работаем маленькими шагами с объяснениями (см. раздел 12).
- Общение на русском.
- ОС разработки: Windows (Git Bash, пути вида `src\app\_layout.tsx`). Тестирование на реальном Android-телефоне.

## 3. Принятые архитектурные решения

### 3.1. Каждый урок — отдельная строка с конкретной датой

Рассматривались две модели: «повторяющиеся слоты + экземпляры на даты» и «одна таблица уроков с датами». **Выбрана вторая**, потому что:

- запрос дня или недели тривиален: `WHERE date = ?`;
- правка урока затрагивает **только этот урок**, прошлое неизменно;
- уведомления строятся напрямую из уроков ближайших дней;
- не нужна логика периодов действия слотов.

Цена: расписание повторяется, поэтому есть кнопка **«Скопировать неделю»**. При копировании **отменённые уроки не копируются**, остальное копируется со сдвигом по дню недели.

### 3.2. Даты и время

- В базе и в стейте дата хранится строкой **`ГГГГ-ММ-ДД`** (`"2026-12-25"`). Она сортируется как текст, работают запросы `date >= ? AND date <= ?`.
- Время хранится строкой **`ЧЧ:ММ`** с ведущим нулём (`"08:30"`). В бизнес-логике (`schedule.ts`) для сравнения и разности переводится в **минуты от начала суток** (`toMinutes`).
- Для пользователя форматируем **только в момент вывода**: `formatDateRu("2026-12-25")` → `"25.12.2026"`.
- **Никогда не использовать `toISOString()`** для дат: он возвращает UTC, и вечером можно получить вчерашнюю дату. Все функции работают в локальном времени.
- Неделя начинается с **понедельника**. `weekday` в JS: воскресенье = 0, поэтому везде есть пересчёт `getDay() === 0 ? 7 : getDay()`.
- **Границы урока согласованы везде:** урок текущий при `start <= now < end`; ровно в `end` он уже прошедший (`end <= now`).

### 3.3. Где что живёт

- **Локальный `useState`**: поля формы урока и `now` на экране «Сегодня» (временные данные одного экрана).
- **Zustand**: список уроков открытой недели (`lessons`) и список уроков **сегодняшнего дня** (`todayLessons`), плюс действия над ними. Он нужен нескольким экранам и будущей синхронизации уведомлений.
- **Прямое обращение к БД** допустимо для разовых чтений (например, `getLessonById` в форме, `countLessonsForWeek` в окне копирования).
- **Все изменения данных идут через стор** (`saveLesson`, `removeLesson`, `copyWeek`), чтобы в одном месте (`refresh`) обновлять и неделю, и «сегодня», и позже вызывать `syncNotifications`.
- **Компоненты** (`LessonCard`, `NowCard`, `DayCard`) не получают колбэки через пропсы (владелец не любит prop drilling). Они берут действия из хука `useLessonActions`, а пропсами получают только данные.

### 3.4. Уведомления

Главный принцип сохранён: **одна функция `syncNotifications(db)`** полностью пересобирает план из базы на скользящее окно (`SCHEDULER_WINDOW_DAYS`): от сегодняшней даты до даты через 7 дней включительно, то есть до 8 календарных дат. Но вместо разовых «скоро конец» и «следующий урок» теперь строится цепочка **состояний одного живого уведомления**: в шторке в каждый момент одно уведомление приложения. Библиотека: **`react-native-notify-kit`** (форк Notifee, API совместимо). `expo-notifications` остаётся для разрешения на показ, `setNotificationHandler` и разовой очистки запланированных уведомлений прежней схемы.

**Состояния** (чистая логика, `src/domain/statusTimeline.ts`, `buildStatusTimeline(lessons, now)` → `StatusStep[]`). Для каждого неотменённого урока:

| Состояние  | Показывается                                                                                         | Исчезает            | Текст                                                                 | Канал            |
| ---------- | ---------------------------------------------------------------------------------------------------- | ------------------- | --------------------------------------------------------------------- | ---------------- |
| `upcoming` | с конца предыдущего урока дня; для первого урока дня за `FIRST_LESSON_STARTING` (60) минут до начала | в начале урока      | «Следующий урок у 5А», время, кабинет, тема                           | `status-v1`      |
| `current`  | в начале урока                                                                                       | за 5 минут до конца | «Идёт урок у 5А», время, кабинет, тема                                | `status-v1`      |
| `ending`   | за `LESSON_ENDING_MINUTES` (5) минут до конца                                                        | в конце урока       | Заголовок «Скоро конец урока», текст «Урок заканчивается в {endTime}» | `ending-soon-v3` |

Состояние добавляется только если `showAt < hideAt`: при уроках без перемены `upcoming` пропускается (сразу `current`), у слишком коротких уроков нет `ending`. После последнего урока дня уведомление просто исчезает. Прошедшие состояния отбрасываются, идущее прямо сейчас показывается сразу.

**Планировщик** (`src/notifications/scheduler.ts`):

- У каждого шага уникальный `id` вида `status-<lessonId>-<kind>`. **Триггеры с одним `id` схлопываются в один** (проверено), поэтому общий `id` для цепочки использовать нельзя.
- Каждое уведомление ставится с `timeoutAfter` = время до следующего состояния и исчезает само, когда наступает следующее. Так в шторке остаётся одно уведомление (проверено).
- Будущие состояния: `createTriggerNotification` с `TriggerType.TIMESTAMP` и `alarmManager: { allowWhileIdle: true }`. Срабатывают по таймеру системы, открывать приложение для этого не нужно.
- Идущее состояние показывается сразу через `displayNotification` (`onlyAlertOnce: true`, чтобы не вибрировать повторно при пересборке).
- Обратный отсчёт: `showChronometer: true`, `chronometerDirection: 'down'`, `timestamp` = начало урока для `upcoming` и конец урока для остальных (системный таймер в шапке уведомления, `мм:сс`).
- `doSync`: сбрасывает остатки прежней схемы (`cancelAllScheduledNotificationsAsync` из `expo-notifications`), отменяет запланированные триггеры (`cancelTriggerNotifications`), убирает показанные уведомления, которых нет в новом плане (удалили или отменили урок), показывает идущее и планирует будущие.
- `syncNotifications` выстраивает вызовы в очередь (`lastSync` на уровне модуля), чтобы параллельные вызовы не перемешивали отмену и планирование.

Вызывается:

- после любого сохранения, удаления или копирования уроков (в конце `refresh` в сторе, без `await`, с `.catch`);
- при запуске приложения и при возврате из фона (хук `useNotificationSync`, вызывается в `(tabs)/_layout.tsx`);
- в фоновой задаче раз в сутки (необязательно, шаг B4.5).

Тексты (`src/domain/notificationTexts.ts`) собираются чистыми функциями без React, БД и библиотек уведомлений; `scheduler.ts` только вызывает их и планирует.

**Каналы Android** (`src/notifications/channels.ts`, константы `CHANNELS`, создаются через `notifee.createChannel`):

| Ключ         | id канала        | Важность | Особенности                                                              |
| ------------ | ---------------- | -------- | ------------------------------------------------------------------------ |
| `status`     | `status-v1`      | LOW      | без звука и вибрации, `visibility: PUBLIC`                               |
| `endingSoon` | `ending-soon-v3` | HIGH     | `vibrationPattern: [400, 200, 400, 200, 400, 200]`, `visibility: PUBLIC` |

Настройки канала (вибрация, звук, видимость) **нельзя изменить после создания**: новое значение требует нового id (`-v4`) и удаления старого. Старые каналы `ending-soon-v1/v2` и `next-lesson` могли остаться на телефоне.

**Инициализация при старте:** `initNotifications()` в `src/notifications/init.ts` (сначала `setupChannels()`, потом `ensureNotificationPermission()` через `expo-notifications`: разрешение системное, одно на приложение; на Android 13+ запрос показывается после создания канала). Вызывается из `useEffect(() => { initNotifications(); }, [])` в `_layout.tsx`. `Notifications.setNotificationHandler(...)` в `_layout.tsx` остался от прежней схемы.

**Точные будильники** (`SCHEDULE_EXACT_ALARM`) не подключали. **Экономия батареи** откладывала или подавляла запланированные уведомления; после снятия ограничения для приложения всё заработало (подсказка для пользователей: шаг C).

## 4. Структура проекта

Важно: папка **`app` лежит внутри `src`** (так создаёт актуальный шаблон Expo). Алиас импортов **`@/`** указывает на `src/`. Схема приложения (`scheme` в `app.json`): `scheduler`.

```
    (tabs)/

  components/
    LessonCard.tsx

    DayCard.tsx
    CopyLessonsModal.tsx
    PickerField.tsx
  db/
    migrate.ts
    lessons.ts
  domain/
    types.ts
    dates.ts
    constants.ts                # WEEKDAYS, REFRESH_LESSONS_MS, LESSON_ENDING_MINUTES, FIRST_LESSON_STARTING, SCHEDULER_WINDOW_DAYS
    schedule.ts                 # getCurrentAndNextLessons, lessonIsPassed, formatDuration, toMinutes
    notificationTexts.ts        # buildEndingText, buildNextLessonText, buildCurrentLessonText
    statusTimeline.ts           # buildStatusTimeline: план состояний уведомления
  hooks/
    useLessonActions.ts
    useNotificationSync.ts      # syncNotifications при старте и возврате из фона
  notifications/
    channels.ts                 # CHANNELS (status-v1, ending-soon-v3), setupChannels (notify-kit)
    permissions.ts              # ensureNotificationPermission
    init.ts                     # initNotifications
    scheduler.ts                # syncNotifications (очередь вызовов, react-native-notify-kit)
  store/
    lessonsStore.ts
```

Правила:

- В `src/app/` лежат **только экраны** с `export default`. Компоненты внутрь не класть: expo-router воспримет их как маршруты.
- Компоненты: именованный экспорт, один компонент = один файл, стили в том же файле.
- Файлы уведомлений живут в `src/notifications/`.

### Навигация

- `app/_layout.tsx`: `SQLiteProvider databaseName="schedule.db" onInit={migrateDb}` оборачивает `Stack` с `headerShown: false`. Есть `export const unstable_settings = { initialRouteName: "(tabs)" }`.
- `app/(tabs)/index.tsx`: редирект с `/` на `/today`. Нужен, потому что dev-клиент открывает приложение по ссылке `scheduler:///`, а маршрута для корня иначе нет.
- `app/(tabs)/_layout.tsx`: `Tabs` с экранами `today`, `week`, `settings`; иконки Ionicons (`today-outline`, `calendar-outline`, `settings-outline`).
- `lesson` открывается через `router.push({ pathname: '/lesson', params: { date } })` для нового урока или `{ id: String(id) }` для редактирования. Режим формы определяется по наличию `id`.

## 5. Модель данных

### Тип (`src/domain/types.ts`)

```ts
export interface Lesson {
    id: number;
    date: string; // "2026-10-05"
    startTime: string; // "08:30"
    endTime: string; // "09:15"
    className: string;
    room: string;
    topic: string; // пусто, пока не вписана
    cancelled: boolean;
}

// для окна копирования недели
export interface CopyLessonsSource {
    start: Date;
    count: number;
}

export interface CurrentAndNextLessons {
    current: Lesson | null;
    next: Lesson | null;
    minutesLeft: number | null;
    minutesToNext: number | null;
}

// состояния живого уведомления (см. 3.4)
export type StatusKind = 'upcoming' | 'current' | 'ending';

export type StatusStep = {
    id: string; // `status-<lessonId>-<kind>`, уникален для каждого шага
    kind: StatusKind;
    lesson: Lesson; // урок, о котором уведомление
    next: Lesson | null; // следующий неотменённый урок того же дня (сейчас в текстах не используется)
    showAt: Date; // когда показать
    hideAt: Date; // когда исчезнет само
};
```

### Схема SQLite (`src/db/migrate.ts`)

Версионирование через `PRAGMA user_version`. Текущая версия схемы: **1**.

```sql
CREATE TABLE lessons (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  date TEXT NOT NULL,
  start_time TEXT NOT NULL,
  end_time TEXT NOT NULL,
  class_name TEXT NOT NULL,
  room TEXT NOT NULL,
  topic TEXT NOT NULL DEFAULT '',
  cancelled INTEGER NOT NULL DEFAULT 0
);
CREATE INDEX idx_lessons_date ON lessons(date);
```

Схема миграции: блоки `if (current < N) { ... }` идут по порядку, в конце `PRAGMA user_version = DATABASE_VERSION`. Для новой таблицы или колонки нужно поднять `DATABASE_VERSION` и добавить новый блок `if (current < N)`. Не менять существующие блоки.

### Функции БД (`src/db/lessons.ts`)

В БД имена в `snake_case`, в коде `camelCase`; перевод делает `rowToLesson`. Все значения в SQL подставляются через `?`.

| Функция                                    | Назначение                                                                                                            |
| ------------------------------------------ | --------------------------------------------------------------------------------------------------------------------- |
| `getLessonsForDate(db, date: Date)`        | уроки одного дня                                                                                                      |
| `getLessonsForWeek(db, monday: Date)`      | уроки недели (пн–вс), по дате и времени                                                                               |
| `countLessonsForWeek(db, monday)`          | количество уроков недели (для окна копирования)                                                                       |
| `getLessonById(db, id)`                    | один урок или `null`                                                                                                  |
| `addLesson(db, lesson)`                    | добавить                                                                                                              |
| `updateLesson(db, id, lesson)`             | изменить только этот урок                                                                                             |
| `deleteLesson(db, id)`                     | удалить (физически)                                                                                                   |
| `copyWeek(db, sourceMonday, targetMonday)` | копирование недели в транзакции; темы сохраняются (комментарий в `lessons.ts` устарел), отменённые уроки пропускаются |
| `getLessonsForRange(db, from, to)`         | уроки диапазона дат включительно, по дате и времени (для планировщика)                                                |

`getLessonsForRange` используется планировщиком (`syncNotifications`) для диапазона от сегодняшней даты до даты через 7 дней включительно; `getLessonsForWeek` для этого не подходит из-за границы недели. Отменённые уроки функция не фильтрует, это делает `buildStatusTimeline`.

### Хелперы дат (`src/domain/dates.ts`)

`toDateString(Date)`, `parseDate(string)`, `addDays(Date, n)`, `startOfWeek(Date)` (понедельник), `daysBetween(a, b)`, `formatShort(Date)` → «5 окт», `formatWeek(monday)` → «5 окт – 11 окт», `formatDateRu(string)` → «25.12.2026», `timeToDate("08:30")`, `dateToTime(Date)`. Для планировщика: `toDate(date: string, time: string): Date`, например `("2026-10-13", "08:30")` → локальный `Date`. Месяц в `new Date(y, m, d)` считается с нуля.

### Логика расписания (`src/domain/schedule.ts`)

Чистые функции без React и БД:

- `toMinutes("08:30")` → `510`;
- `getCurrentAndNextLessons(lessons, now)` → `{ current, next, minutesLeft, minutesToNext }`; отменённые игнорируются, текущий: `start <= now < end`, следующий: первый неотменённый с `start > now`; `lessons` должны быть уроками **одного дня** с `now`;
- `lessonIsPassed(lesson, now)` → `end <= now`;
- `formatDuration(minutes)` → «35 мин», «1 ч 15 мин», «2 ч».

### Zustand (`src/store/lessonsStore.ts`)

Состояние: `weekStart: Date | null`, `lessons: Lesson[]` (открытая неделя), `todayLessons: Lesson[]` (сегодня).
Действия: `loadWeek(db, weekStart)`, `loadToday(db)`, `removeLesson(db, id)`, `saveLesson(db, id | null, data)`, `copyWeek(db, source, target)`.

Внутренний хелпер `refresh(db)` перезагружает открытую неделю (если `weekStart` задан) и «сегодня», а затем без ожидания вызывает `syncNotifications(db)` (с `.catch` и предупреждением в консоль): одна строка покрывает сохранение, удаление и копирование. Все изменяющие действия заканчиваются вызовом `refresh`. Функции БД импортируются с псевдонимами (`addLesson as dbAddLesson`, `copyWeek as dbCopyWeek`), чтобы не путаться с одноимёнными действиями стора.

### Хук (`src/hooks/useLessonActions.ts`)

Возвращает `{ addLesson(dateStr), openLesson(id), confirmRemove(id) }`. Внутри навигация через `router`, подтверждение удаления через `Alert.alert`, само удаление через стор.

### Хук (`src/hooks/useNotificationSync.ts`)

Через `useSQLiteContext()` вызывает `syncNotifications(db)` при запуске и при возврате приложения на передний план (`AppState` → `active`), с `.catch` и предупреждением в консоль; подписка снимается при размонтировании. Вызывается в `(tabs)/_layout.tsx` (внутри `SQLiteProvider`).

## 9. Подводные камни и найденные грабли (чтобы не повторять)

- **Любой текст должен быть внутри `<Text>`.** Лишняя `;` между тегами в JSX даёт ошибку «Text strings must be rendered within a <Text> component»: `<Stack ... />;` внутри провайдера.
- **`{x && <Comp/>}` с числом:** если `x === 0`, React Native попытается нарисовать `0` как текст вне `<Text>` и упадёт. Сравнивать явно (`x !== null`, `x > 0`).
- **`tabBarIcon: () => { <Icon/> }`**: с фигурными скобками нужен `return`, иначе иконка не рисуется. Либо `=> ( <Icon/> )`.
- **`useFocusEffect` требует колбэк в `useCallback`**, иначе бесконечный цикл. Нужен вместо `useEffect` на вкладках, потому что вкладки не размонтируются. Таймеры (`setInterval`) внутри него обязательно очищать в возвращаемой функции.
- **Типы маршрутов expo-router** генерируются при старте сервера: после добавления нового экрана перезапустить `npx expo start --dev-client -c`.
- **«Unmatched Route, Page could not be found `scheduler:///`»** в dev-клиенте: нет маршрута для `/`. Решение: `src/app/(tabs)/index.tsx` с `<Redirect href='/today' />`. В Expo Go это не проявлялось.
- **`key` ставится на элемент в массиве** (в `week.tsx` на `<DayCard key=...>`), а не внутри самого компонента.
- **Старая ошибка**: в `addTest` стоял `addDays(weekStart, -Math.floor(...))` с минусом, и уроки уходили в прошлую неделю. Функция должна быть удалена.
- **Android 12+:** точное срабатывание уведомлений требует разрешения на точные будильники.
- **Каналы Android неизменяемы** по звуку и вибрации после создания. Менять паттерн только созданием канала с новым id.
- **Android 13+:** запрос `POST_NOTIFICATIONS` показывается, только когда канал уже создан, поэтому порядок в `initNotifications`: каналы, затем разрешение.
- **Нативные пакеты требуют пересборки dev-клиента.** Одного `npm install` мало: старый APK не содержит нового нативного кода. JS-изменения пересборки не требуют.
- **Данные SQLite в dev-сборке отдельные** от Expo Go (другое приложение): тестовые уроки нужно создавать заново.
- **Цвет текста в RN не наследуется** от родителя: красить каждый `<Text>` (исключение: `<Text>` внутри `<Text>`).
- **Вложенные вертикальные списки нельзя** (`FlatList` в `FlatList`/`ScrollView`): для нескольких секций использовать `SectionList` или `ListHeaderComponent`/`ListFooterComponent`.
- `async` нельзя передавать напрямую в `useEffect`: использовать `(async () => { ... })()` либо вызывать отдельную async-функцию с фигурными скобками `useEffect(() => { fn(); }, [])` (стрелка без скобок вернула бы Promise).
- Пикер даты `DateTimePickerAndroid.open` работает только на Android (цель проекта именно она).
- `expo-doctor` может ругаться на патч-версии внутри SDK: это не ошибка, обновляется `npx expo install --fix`.
- **Триггеры с одним `id` схлопываются.** Если запланировать несколько уведомлений с одинаковым `id` (проверено в `react-native-notify-kit`), останется только последнее. Цепочку заранее запланировать так нельзя: у каждого шага уникальный `id` (`status-<lessonId>-<kind>`), а замену в шторке обеспечивает `timeoutAfter`.
- **`timeoutAfter`** (мс) убирает показанное уведомление само. Для цепочки состояний ставится равным времени до следующего состояния, тогда в шторке всегда одно уведомление.
- **Обратный отсчёт в уведомлении** даёт только системный хронометр (`showChronometer` + `chronometerDirection: 'down'` + `timestamp` как цель отсчёта): он рисуется в шапке уведомления в формате `мм:сс`. Поминутный текст внутри уведомления без foreground-сервиса не сделать.
- **Android 14+ позволяет смахивать «постоянные» (ongoing) уведомления**, кроме особых случаев (плеер, звонок, VPN-сервисы вроде Hiddify). Гарантировать «нельзя смахнуть» для приложения расписания нельзя; `sticky`/`ongoing` пока не делаем.
- **Хук с `useSQLiteContext()` вызывается только внутри `SQLiteProvider`.** Поэтому `useNotificationSync()` стоит в `(tabs)/_layout.tsx`, а не в корневом `_layout.tsx`, где провайдер рендерится.
- **Предупреждение `[notifee] no background event handler has been set`:** на работу планировщика не влияет. Обработчик `notifee.onBackgroundEvent(...)` нужен для кнопки «Закрыть» и регистрируется на верхнем уровне модуля (не в `useEffect`).
- **Уведомление в несуществующий канал на Android 8+ не показывается.** Если какое-то состояние не появляется, проверить `notifee.getChannels()` и порядок: каналы создаются раньше, чем планируется уведомление. Точная причина единственного такого сбоя в ходе разработки не установлена, после повторной проверки всё заработало.
- **Логи для диагностики планировщика:** после планирования смотреть `notifee.getTriggerNotificationIds()` и `notifee.getChannels()`. Не вешать диагностику на `useFocusEffect` в layout: он срабатывает раньше, чем `syncNotifications` закончит работу, и показывает пустой список.
- **`react-native-notify-kit` работает только в development build** (Expo Go не поддерживается), нужен config plugin в `app.json` и пересборка dev-клиента. Библиотеку поддерживает один разработчик (форк Notifee); логика расписания от неё не зависит.

## 11. Соглашения по коду

- TypeScript, функциональные компоненты, именованный экспорт компонентов, `default export` только у экранов в `src/app/`.
- Импорты через алиас `@/…`.
- Одинарные кавычки (в том числе в JSX-атрибутах), отступ 4 пробела (так форматирует владелец).
- Стили: `StyleSheet.create` в конце того же файла. Акцентный цвет `#4a4ae0`, серый `#888`; карточки уроков белые (`#fff`), класс синим `#056ccc`, отменённые `#cfcfcf` / `#8f8f8f`; акцентная карточка «Текущий урок» `#4a4ae0` с белым текстом.
- Бизнес-логика (текущий/следующий урок, формирование текстов уведомлений) выносится в чистые функции в `src/domain/`, без React и без БД.
- Работа с БД только в `src/db/`; наружу отдаёт camelCase-типы.
- Работа с уведомлениями только в `src/notifications/`; показ и планирование через `react-native-notify-kit`, `expo-notifications` остаётся только для системного разрешения, `setNotificationHandler` и разовой очистки старых запланированных уведомлений. Тексты уведомлений и план состояний собираются в `src/domain/`.
- Любое изменение уроков идёт через действия стора, не напрямую через БД.
- Машинный формат даты (`ГГГГ-ММ-ДД`) везде внутри, форматирование только при выводе.
- Константы (интервалы, названия дней, `LESSON_ENDING_MINUTES`, `FIRST_LESSON_STARTING`, `SCHEDULER_WINDOW_DAYS`) в `src/domain/constants.ts`.

## 12. Как со мной работать (инструкция для ИИ/агента)

- Я **учусь React Native**, поэтому не сваливай всё сразу. Делай **один небольшой шаг за раз**, объясняй что и зачем, особенно отличия от веб-React (`View`/`Text`, `StyleSheet`, `Pressable`, `FlatList`, хуки навигации).
- Давай полный код файлов, которые нужно создать или изменить, с указанием **точного пути** (учитывай, что `app` внутри `src`, алиас `@/`).
- После каждого шага давай короткую **проверку** («что должно получиться») и маленькое **задание** для закрепления.
- Не навязывай новые библиотеки без причины. Сначала предложи и объясни выбор.
- Если я присылаю ошибку или свой код, найди причину и объясни её, а не просто выдай исправление.
- Отвечай по-русски, без воды.
- Я часто сам улучшаю предложенный код (например, сам перешёл на `SectionList`, переименовал функции): перед правками сверяйся с присланным кодом, а не с тем, что было выдано ранее.
- Владелец сам решает, какие функции делать: утреннее уведомление и блок «Далее:» в тексте уведомления он отклонил. Не возвращай их без запроса.
- Перед предложением архитектуры с нативной библиотекой проверяй её возможности по документации или коротким тестом на телефоне, а не по догадке (так выяснилось, что триггеры с одним `id` схлопываются, см. раздел 9).
- Следующий шаг по плану: завершить **B4.1** — проверить типы и прогнать сценарии уведомлений на телефоне; затем вернуться к **B4.2**. Подробности в разделе 8.
